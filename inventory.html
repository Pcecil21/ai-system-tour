Two assistants, shared project files

I use Claude Code and Codex for hands-on work with files, research, documents, and software. The workspace gives the assistant access to the project and the tools that task needs.

Their native conversations are separate. Shared instructions and handoffs make it possible to continue the work in either tool.

Claude CodeWorks in the terminal and editor with project instructions, local skills, hooks, and configured tool servers.
CodexWorks with the same project files, with app and editor workflows, specialist reviews, connected tools, and document or design capabilities.
The project folderHolds the actual source, working documents, decisions, tests, and handoff. It is the continuity point when a chat ends or a workspace changes.

Start from the current state

The assistant reads the project instructions, recent handoff, and relevant files, then checks the current working state. Saved context helps orient the work; it still needs to be checked.

Claude Code has scoped startup and retrieval hooks. Codex follows the shared project instructions and can read the same handoff. Context and tool access vary by workspace.

InstructionsCLAUDE.md and AGENTS.md describe the project, conventions, and boundaries that apply to the task.
Handoffs and decisionsHANDOFF.md and decision logs record what changed, what remains, and why earlier choices were made.
Retrieved knowledgeObsidian notes and the configured Brain MCP search layer help locate relevant project or research context. Source files remain important when summaries are incomplete or out of date.
Current evidenceFiles, git changes, test results, and tool responses establish what is present now. An old plan or status note does not prove something is running.

Use the right instructions for the job

Skills provide a repeatable way to handle particular work: planning, research, writing, document creation, design, or code review. Specialist agents can take a focused part of a larger task.

Selection follows the request and available capabilities. The skill router helps resolve overlaps; it is not a fixed keyword switchboard. Installed libraries are broader than the tools used in any one session.

Personal playbooksLocal instructions capture recurring work, project conventions, output formats, and review steps.
Plugin capabilitiesEnabled packages add tools and workflows for documents, presentations, spreadsheets, browsers, design, and development.
Specialist reviewsFocused roles can inspect correctness, security, architecture, tests, or visual design. A role is an available capability, not a person or a permanently running worker.
Task-specific combinationsA task may use several capabilities in sequence. Only the tools relevant to the current work need to be involved.

Make the result reviewable

A useful result is something I can inspect: a sourced research note, an editable document, a tested change, or a working preview. The checks depend on the kind of work.

Saving a file, committing code, publishing a site, and sending a message are different actions. Each follows the authorization and boundaries of the task.

Research checksResearch workflows retain source material and can use separate challenge and citation-review steps.
Software checksBuilds, tests, browser verification, and focused code reviews check the actual change.
DeliverablesDocuments, spreadsheets, presentations, PDFs, and previews give me something concrete to review or use.
Release decisionsExternal messages, publication, and production changes follow the relevant approval and task instructions. A completed draft is not automatically sent.

What do these terms mean?

Playbook / skill — Instructions, templates, or tools for a particular type of work. A skill is loaded when it fits the task.

Specialist / agent — An AI role with a focused assignment, such as reviewing code or testing a plan.

Connection / MCP — A tool interface to a service or local capability. Configuration, permission, and connection health are separate.

Vault / notebook — A collection of linked local notes. Relevant notes can be read and updated as part of the work.

Hook / scheduled task — A hook reacts to a session event. A scheduled task has a registered time or trigger. Neither means every action is automatic.

06 — Safeguards

The boundaries around the work.

The system uses scoped instructions, permissions, checks, and review steps. Their coverage depends on the tool and workflow; none replaces care with sensitive information.

Specific controls, with their limits understood.
Separate information scopesProject instructions define which information a workflow may use. General research context and sensitive practice work have different boundaries and retrieval rules.
Checks around file changesConfigured hooks look for common sensitive identifier patterns and selected risky operations. Some checks warn or audit after a write, so they support review rather than replace it.
Bounded tool accessConnections and permissions differ by project and assistant. A tool being installed does not make it authorized for every task or connected in every session.
Review before consequential useSensitive inputs, client-facing work, messages, and production changes follow the review and authorization steps for that workflow. I remain responsible for what is used or shared.
The tools help carry the work. I do the judgment work.
